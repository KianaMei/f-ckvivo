## 已有实现与新路线

### 通用白名单已运行

- 拖放直达 `com.vivo.globaldragdrop`：入口和异步抓取两处范围，真实 EnhancedConfigBean。
- 内容提取服务 `com.vivo.accessibilityenhance`：只在调用方为拖放直达、business=dragdrop 时放行来源名单，保留原有其他检查。
- 曾实测名单外的普通原生 TextView 正确提取，问题并非只给 PiliBro 放行。

### PiliBro 目前仍直接 hook

PiliBro 精确提取仍用 FlutterSelectionFeature：读取虚拟语义节点、按触点选择内容、图片区域 PixelCopy，再由 SelectedContentFeature 替换回传内容。
用户已确认基本可用，但图片边界仍需优化。**尚未迁移到无来源 hook 方案，不要声称 PiliBro 已无需 scope。**

### ExteraLess：宿主侧调用 vivo 原生组合提取

新文件：

- `src/main/java/dev/ganvivo/dragall/NativeSelectionFeature.java`
- `src/main/assets/telegram-native.json`

只在拖放直达 `vb.p.g(Context,boolean)` 处理已核验客户端时，限定当前线程的请求范围。
把 `AccessibilityManager.requestAccessibilityEnhanceExt` 的 `supportDragDropBusiness` 请求转换为 `generalizeGrab`。
厂商原始 `assets/authorize/CatcherBusinessWhiteList.json` 已允许 dragdrop 调用这个接口及能力等级 4，无需改服务权限或结束 UID 1000 服务。

厂商表达式链支持 PView、方法调用、字段读取、带参数方法、条件分支及 Bitmap 输出：

- PView 按触点定位 ChatMessageCell。
- `getMessageObject().messageText/caption` 取正文/说明，绕开厂商误取 timeLayout 的路径。
- `getPhotoImage().isInsideImage(relativeX,relativeY)` 区分图片与正文；getBitmap 返回实际图片。
- PhotoViewer$FrameLayoutDrawer 可读 this$0.currentMessageObject / centerImage；尚未验证全屏手势是否会向宿主发送请求。
- 拒绝秘密媒体、禁止转发的消息及未揭示剧透。不返回整屏兜底。

客户端没有 Vector scope，也没有安装模块方法 hook。厂商原生提取代码仍会在来源进程内执行反射，不能描述为“完全没有代码进入客户端”。

## 0.1.9、0.1.10 的问题及 0.1.11 修正

### 图片的只写管道问题

0.1.9 的 native_selected_text 已实际命中，用户确认可拖文字。
图片也通过表达式链取到并返回成功，但模块读取厂商 outputUri 验证尺寸时，报 EBADF，随后自行把成功改为失败。

原因：SharedFileProvider 的 tempImage URI 命中特殊分支，openFile 返回写入端管道，数据再由宿主转存到 DragInfo.getUri()。不能把 tempImage 当可读图片。
此外 `vb.p.Q` 的 imageUrl 下载分支只接受 HTTP(S)，不能用本地 content URI 走下载。

0.1.10/0.1.11 的实现改为直接把 Bitmap 同步写入本次 DragInfo.getUri() 的 MediaStore URI，授予当前来源读写权限；成功后校验实际图片，生成最长边不超过 512 的采样预览，设置 widgetType=10、type=image、localBitmap，再调用 DragService.j(30) 走本地图片成功回调。
**这个图片回传方案仍待实机验收。** 需检查 URI 是否有效、来源写权限、预览、实际 ClipData 图片、请求过期保护，以及全屏手势是否进入请求链。

证据：`logs/native-route-metadata-check-0.1.9.txt` 中有 Invalid native image output / read failed EBADF。

### 0.1.10 的加载回归

0.1.10 最初安装被用户拒绝，随后用户明确“快来安装，我刚才在干别的”，重新标准安装成功。
只重建拖放直达，PID 4159 → 31724。加载检查发现：

`NoSuchFieldException: No field f14624n in class Lvb/p;`

`f14624n` 是 JADX 展示的重命名，DEX 真实字段为 **`n:Ljava/lang/ref/WeakReference;`**。
业务组在解析字段时失败，native_selection 未注册，因此 0.1.10 并未恢复 0.1.9 的文字方案。

0.1.11 已改为真实字段 n，且把该字段加入 verify-host.py，避免静态检查再次漏掉。
证据：`logs/native-route-load-failure-0.1.10.txt`、`logs/host-validation-0.1.11.json`。
