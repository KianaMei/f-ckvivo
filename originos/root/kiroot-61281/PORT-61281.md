# kiroot × 6.12.81 移植（2026-11-27，**复核修正版**）

> 目标：把 kiroot 那套「原位改 cred、零常驻内存」的临时 root 从 6.12.58
> （`gdd6fd5c98918` / tag 7742，本机在跑）搬到 6.12.81
> （`6.12.81-android16-6-gc3e244f20fca-abogki576505657-4k`，PD2545 下一版 OTA）。
> 全程离线：只用已归档的 kernel Image + 已装 kiroot 的 APK，不碰设备分区、不装包。

## 1. 结论（2026-11-27 复核后**推翻**当日 17:37 版）

**端口没做完，成品 APK 在 6.12.81 上不能用。** 当日那版写的是「已经做完了，只剩一次实机首测」，
错在把「build 绑定物」数成了 4 个探针字符串。实际上 `poc_tmp_root` 里还内联了 **8 个内核
链接期地址**（`movz/movn/movk` 指令立即数），一个都没改：

| # | 标签 | 6.12.58 的值 | 编码 | 站点（函数+偏移） | 6.12.81 目标值 |
|---|---|---|---|---|---|
| 1 | `load_module` | `0xffffffc080502688` | direct | `seq_run+0x1620` | **`0xffffffc08057c4e4`**（本仓 kallsyms 解出） |
| 2 | `kprobe_aggr_pre_handler` | `0xffffffc0805509bc` | direct | `seq_run+0x16dc` | 待解 |
| 3 | `data_825d7d68` | `0xffffffc0825d7d68` | direct | `seq_run+0x1848` | 待解 |
| 4 | `data_826d93e0` | `0xffffffc0826d93e0` | direct | `seq_run+0xb34` | 待解 |
| 5 | `data_826f4550` | `0xffffffc0826f4550` | direct | `seq_run+0xdb4` | 待解 |
| 6 | `data_8279f6e8` | `0xffffffc08279f6e8` | direct | `seq_run+0x15e0` | 待解 |
| 7 | `data_827c6519` | `0xffffffc0827c6519` | direct | 4 处：`pwn_main+0xd8` / `capsel_main+0x16c` / `modload_main+0xf8` / `seq_run+0x214` | 待解 |
| 8 | `slide_anchor` | `0xffffffc0805173e4` | **negated** | `leak_slide+0x348` | 待解 |

第 8 项最致命：`leak_slide` 里存的是 `-anchor`（即时数 `0x3f7fae8c1c` = `slide = 泄漏值 - 0xffffffc0805173e4`）。
**KASLR slide 本身是用一个 6.12.58 的链接期地址算出来的**，换了 build 之后算出的 slide 会整体偏掉
（58→81 的 `load_module` 就差 `0x79e5c`），随后 `slide + ksu_patch.txt 地址` 全部错位。

`[exit 3]`：`build_61281.py --audit` 现在会直接报「8 个 anchor 里 0 个有目标值」并拒绝出包，
就是为防这类「改了一半的 payload」。

## 2. 证据（可复现）

**2.1 8 个立即数不在任何字符串里，只存在于代码**：`strings`/字节搜索看不到，所以当日只对比
`load_module+0xNNNN` 四串就以为「没有别的 build 相关常量」。用 capstone 按函数扫描 `movz/movn/movk`
链才挖出来（脚本：`cache/scratch/kiroot_audit/hunt_imm.py`、`hunt_neg.py`，一次性审计件，不入库）。

**2.2 其中两个被真机日志钉死**（`device-dump/pd2545-B-17.1.13.20/runtime/tmp2/cseq.log`，6.12.58 实跑）：

```text
CSEQ start slide=0x1ca9000000 ...
AGG addrfield=0xffffffdd29502688 ok=1 expect_load_module=0xffffffdd29502688
AGG pre_handler=0xffffffdd295509bc ok=1 expect_aggr=0xffffffdd295509bc
```

- `0xffffffdd29502688 - 0x1ca9000000 = 0xffffffc080502688` → 第 1 项 = `load_module`，
  与 `kdis` 量出的 6.12.58 span 起点完全一致；
- `0xffffffdd295509bc - 0x1ca9000000 = 0xffffffc0805509bc` → 第 2 项就是 kprobes 内部
  `aggr_pre_handler`（payload 自己读内核里的 `kprobe->pre_handler` 再与 `slide + 常量` 比对，`ok=1`）；
- 第 8 项：`0x3f7fae8c1c` 取反 = `0xffffffc0805173e4`（`leak_slide` 的 `add x19, x1, x8`）。

**2.3 这 8 项都没被当日脚本改过**：`build_61281.py` 当时只做 `payload.replace(旧串, 新串)` 四刀，
代码立即数原样带进成品 APK。

## 4. 还没解出来的 7 个地址怎么解

需要 6.12.81 的 kernel Image（当日只在机械革命 `cache/new.o`，本机没有、`ssh jige` 也不通）。
拿到后的路线：

1. **第 1 项已解**：`0xffffffc080502688 + 0x79e5c = 0xffffffc08057c4e4`（同一次 kallsyms 解码给出的 span 起点），可直接填。
2. **第 2 项**：按符号名 `aggr_pre_handler` 在新 Image 的 kallsyms 里查（静态函数在表内，'t' 类型）。
3. **第 3–8 项**：先用 6.12.58 的 Image + 设备 kallsyms 快照把每个地址对上符号名，再按名查 6.12.81。
   目前只有两条**弱线索**（未证实，别当结论）：
   - `data_826d93e0 = __tracepoint_sys_enter(58 表内 0xffffffc0826d9390) + 0x50`
   - `data_827c6519 = selinux_state(58 表内 0xffffffc0827c6520) - 7`（非 8 对齐，说明它是某结构体字段而不是符号起点，
     这个 `-7` 很可能只是「地址刚巧落在 selinux_state 前 7 字节」，别直接套用到 81）
4. 全部 8 个填齐后：`build_61281.py --anchor L=0x…`（8 次）→ 校验通过 → `repack_apk.py` → zipalign → apksigner。

### 4.1 外部线索（2026-11-28 复核，**未证实**，别当结论用）

| 锚点 | 线索 | 本机可核到什么程度 |
|---|---|---|
| `slide_anchor` | `do_timer_create+0xac` | **序一致**：kallsyms 顺序里 `load_module`(idx 15680) < `do_timer_create`(16000) < `kallsyms_lookup_name`(16315)，与 0x5173e4 所在地址窗一致；但该窗内还有 2750 个符号，**一致≠证实**。若成立，81 值 = `do_timer_create_81 + 0xac`，可按名解 |
| `data_827c6519` | `selinux_state` | **数值差 7 字节**：机器码是 `0xffffffc0827c6519`，`selinux_state` 在 58 表里是 `0xffffffc0827c6520`（81 表 `0xffffffc08290d6c8`）。照字面把 81 的 `0x8290d6c8` 填进去会**偏 7 字节**，等于又一次写错内存。Δ 是「字段偏移」还是「巧合」必须先在 58 Image 上定 |
| `data_825d7d68` / `826d93e0` / `826f4550` / `8279f6e8` | 未命名 | 括号窗分别含 1217 / 8799 / 8799 / 8799 个符号，**用"最近符号±偏移"猜必错**；只能在 58 Image 上反查符号名，再去 81 表里按名取 |
| `kprobe_aggr_pre_handler` | 名字已知（`aggr_pre_handler`，静态函数） | 81 值需在 81 Image 的 kallsyms 里按名查 |

注意 `slide_anchor` 在机器码里是**取反形态**（`0x3f7fae8c1c`），任何"按低 32 位搜 `0x805173e4`"或"搜 `0xffffffc0…`"的做法都找不到它；只能按指令链改。

### 4.2 2026-11-28 收到的问题清单（原文）与实测对照

| 原文条目 | 原文说法 | 实测 | 处置 |
|---|---|---|---|
| `leak_slide()` KASLR 泄漏 | 仍保留 6.12.58 的 `0x1173e4 / 0x805173e4`；须改为 6.12.81 的 `do_timer_create+0xac` 特征；致命阻断（返回 `slide=0`） | 锚点 `0xffffffc0805173e4` 确实在（`leak_slide+0x348`），但载体是**取反形态 `0x3f7fae8c1c`**；`0x1173e4` / `0x5173e4` / `0x805173e4` 在文件里 **u32/u64 各 0 命中**，没有任何可按字搜索的形态 | 身份 `do_timer_create+0xac` 只有序一致性（见 §4.1）：`do_timer_create` 在 kallsyms 序 idx=16000，落在 `load_module`(15680) 与 `kallsyms_lookup_name`(16315) 之间，与该地址窗相符，但**不构成证实** |
| SELinux 原位修补 | 机器码写死 `0x827c6520`；须改为 6.12.81 的 `0x8290d6c8`；致命阻断（写错内存） | 机器码里是 **`0xffffffc0827c6519`**（4 处：`pwn_main+0xd8`、`capsel_main+0x16c`、`modload_main+0xf8`、`seq_run+0x214`），比 `0x827c6520` 早 **7 字节**；`0x8290d6c8` 是 81 表里 `selinux_state` 的**符号值** | **不能照抄**：先定 Δ（-7 是不是结构性字段偏移），否则等于把"写错内存"换成"偏 7 字节写错内存" |
| Kprobe 结构与 tracepoint | 机器码写死 58 的 table/aggr/tracepoint；须改为 81 的对应符号地址 | 对应 5 个锚点：`kprobe_aggr_pre_handler`（`0xffffffc0805509bc`）+ `data_825d7d68` / `data_826d93e0` / `data_826f4550` / `data_8279f6e8`；另有 `load_module`（`0x…502688`）和 `data_827c6519` 不在这三条里 | 逐条按 §1 表解；`aggr_pre_handler` 可按名查，其余四个只能在 58 Image 上反查名字 |

补一条实测（也是第一版踩坑的直接原因）：**这 8 个值没有一个以连续字节出现在 payload 里**（u32/u64 全 0 命中），全部拆进 `movz/movn/movk` 的 imm16 字段。所以"搜数值→替换"的方案物理上不成立，只能按指令链改写——现工具的 `scan_anchors` / `patch_chain` 走的就是这条路，并且回读校验。



## 5. 复现（路径已按 `system/`→`originos/` 更名修正，outdir 已统一）

```bash
# 0) 审计：先看这 8 个内联地址有没有目标值（缺就退出码 3，不出包）
python originos/root/kiroot-61281/tools/build_61281.py --audit

# 1) 重建 payload + 表（输入为 6.12.81 的 Image 或其 ELF 包装；8 个 anchor 必须齐）
python originos/root/kiroot-61281/tools/build_61281.py \
  --image cache/new.o --outdir cache/scratch/kiroot_61281 \
  --anchor load_module=0xffffffc08057c4e4 \
  --anchor kprobe_aggr_pre_handler=0x… \
  --anchor data_825d7d68=0x… --anchor data_826d93e0=0x… \
  --anchor data_826f4550=0x… --anchor data_8279f6e8=0x… \
  --anchor data_827c6519=0x… --anchor slide_anchor=0x…

# 2) 换进 APK（会校验源 APK 指纹、丢掉旧 v1 签名条目）
python originos/root/kiroot-61281/tools/repack_apk.py

# 3) 对齐 + 重签（签名与机上现装的 kiroot 不同，安装前要卸旧版）
"$SDK/build-tools/36.1.0/zipalign.exe" -f -p 4 \
  cache/scratch/kiroot_61281/kiroot-81-unsigned.apk \
  cache/scratch/kiroot_61281/kiroot-81-aligned.apk
"$SDK/build-tools/36.1.0/apksigner.bat" sign --ks shared/signing/debug.keystore \
  --ks-pass pass:android --key-pass pass:android --ks-key-alias androiddebugkey \
  --out cache/scratch/kiroot_61281/kiroot-81.apk \
  cache/scratch/kiroot_61281/kiroot-81-aligned.apk
```

产物补充：`build_61281.py` 现在会写 `retarget-manifest.json`（每个 anchor 的旧值/新值/站点、
payload 前后 sha256、改动字节数），出包前以它为准核对。
