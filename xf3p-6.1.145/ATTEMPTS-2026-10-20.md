# X Fold3 Pro 6.1.145 二次进攻记录（2026-10-20 下午）

设备：vivo PD2337 / V2337A，OriginOS 6，16.2.18.6，内核
`6.1.145-android14-11-maybe-dirty`，SPL 2026-08-01。
结论先行：**仍未拿到 root**；但本轮把三条路线的可行性全部钉死，且设备零数据损伤
（失败均为内核 panic 自动重启，或安全失败）。

## 1. KSuRoot 官方基线路线：死（路线选错）

`libbaseline_6_1.so` + 本机偏移构建的 `payload-vivo.so`（175776 B，vivo 闸门 PASS）
经 KSuRoot helper 注入后，日志显示它加载的是 **tokay / Pixel 9 的 pselect 配置**
（`label=p9_cp2a_260605_012_truephone slide=pselect main=pselect`，
`init_task=0x201f640` 而非本机 `0x21dfc00`），随后 `KernelSnitch mm_struct leak failed`
→ 重试 → 内核 panic 重启。原因：该基线是 tokay（Pixel 9）的 pselect 路线，
本机 pselect 栈几何不成立（见 §3）。

## 2. pd2324 6.1.145 参考路线：tracefs KASLR 成功，但 pselect 几何死

把 `CyberMeowfiaNS/examples/pd2324-6.1-reference` 的完整源码编译成本机 target
（`pd2324-xf3p/src/targets/XF3P-BP2A.250605.031.A3/target.h`，符号全部来自本机 kallsyms）：

- **tracefs KASLR 泄漏实测成功**：`KASLR_ONLY=1` 模式下
  `tracefs text-base candidates uniq=8 top=ffffffd0c44f099c count=22209
  minus_off=ffffffd0c4200000` → 本机构建的 `TRACEFS_KPTR_OFF = 0x2F099C`
  （符号 `tracing_mark_write`），运行时 text base `0xffffffd0c4200000`。
- **但 fake-lock 的 pselect 栈几何不可行**。反汇编本机内核：
  - `core_sys_select`：`sub sp,#0x1c0`，`stack_fds = sp+0x50`
  - `__arm64_sys_pselect6`：`sub sp,#0x90`
  - `__arm64_sys_futex`: `sub sp,#0x70` → `do_futex`: `sub sp,#0xd0` →
    `futex_wait_requeue_pi`: `sub sp,#0x1c0`；`rt_mutex_waiter` 在 `sp+0x28`
  - 于是 fd_set 在 `SP_top-0x200`，waiter 在 `SP_top-0x2d8`：
    **waiter 比 fd_set 低 0xd8 字节 = −27 个 8 字节字（−216 字节）**，
    与官方 extractor 的 `pselect overlap -216` 一致。
    伪造 waiter 的 tree_entry/pi_tree_entry 整段落在 fd_set 覆盖范围之外，
    无法控制；写全 fake waiter 的 shift 必须 ≥ 0，而本机构建是 −27。
- 实机验证：`shift=0` 与 `shift=1`（extractor 值）都在 consumer 触发
  `sched_setattr` 后立刻 panic；安全失败，无数据损伤。
- 结论：pd2324 的 pselect/fake-lock 路线**在本构建上结构性不可行**，
  与官方 extractor “pselect route not feasible → 6.1 走 tcp_zerocopy”的判定一致。

## 3. 官方 / alfxki tcp_zerocopy 路线：UAF 命中，但 W1 写不落地

用 alfxki fork 的 CLI（`ghostlock_alf`）加载本机 bin（route=1 tcp_zerocopy）：
- 不再 panic；W1 每轮 `tcp route done=1 calls=1 success=1 status=0 clean=1/1`，
  即 UAF 原语命中。
- 但 SELinux 写验证失败：15/15 轮后 `[-] Write 1 failed`，
  `/sys/fs/selinux/enforce` 始终为 1。
- 两种物理加载地址都试过：
  - `kernel_phys_load=0xA8000000`（extractor/SoC 公式）：target `0xffffff802a558f40`
  - `kernel_phys_load=0x80000000`（X300 Pro 验证过的 pair）：target `0xffffff8002558f40`
  两者都写不进去。第二种每次都被 page picker 以
  `stores an even byte over selinux_state.initialized` 拒绝（15/15）。
- 已确认 `CONFIG_SECURITY_SELINUX_DISABLE` 未开启 → `selinux_state.enforcing` 在 byte 0，
  偏移本身正确；`SELINUX_ENFORCING_OFF=0x2558f40` 无误。
- 结论：tcp 路线能稳定触发漏洞，但当前 profile 的“物理页 → 直接映射别名”仍不对，
  或 tcp 写原语在本机构建上的落点参数需要按构建重标定。没有 panich 风险，
  可以继续调参（物理 pair / arm_sequence / hold），但单靠现有公开 profile 不足以收尾。

## 4. 设备状态

- 未获得 root；未改动 boot/分区；未写入用户数据。
- 多次失败均为内核 panic 自动重启（uptime 归零），重启后系统正常。
- 测试结束后已关闭 tracefs 事件与 tracing_on。
- 屏幕仍处于锁屏（人脸 + 密码），adb 路线不需要解锁；App UI 需要用户解锁。

## 5. 可继续的方向

1. 用本机 kallsyms 反推真实 `_text` 物理地址（需 page-table/物理读原语或 bootloader 日志），
   把 `kernel_phys_load` 钉死，再试 tcp W1。
2. 调 tcp 写原语参数（`arm_sequence`/`post_receive_hold_iterations`）并观察 page picker
   是否不再报 `initialized`。
3. 等社区发布 `6.1.145-android14-11-maybe-dirty`（PD2337 16.2.18.6）专用 profile；
   或从官方 6.1.145 其他机型 profile（如 alfxki 的 `g09f1c007...` 档）反查物理 pair 差异。
